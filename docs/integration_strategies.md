# Сравнение стратегий интеграции

| Стратегия | Преимущество | Недостаток | Когда подходит |
|---|---|---|---|
| Нисходящая | Можно рано проверить верхний уровень | Для нижних модулей могут понадобиться заглушки | Когда важен интерфейс и управление системой |
| Восходящая | Можно рано проверить вычислительные модули | Для их запуска могут понадобиться драйверы | Когда сначала готовы нижние уровни системы |
| Сэндвич-интеграция | Верхние и нижние уровни можно проверять параллельно | Сложнее организовать их последующее соединение | Для многоуровневых проектов |
| Риск-ориентированная | Позволяет раньше обнаруживать наиболее опасные проблемы | Необходимо определить и оценить риски | Когда отдельные взаимодействия особенно сложны или важны |
| Функционально-ориентированная | Можно проверять систему по готовым функциям | Одна функция может затрагивать несколько модулей | Когда важна последовательная готовность пользовательских функций |
| Т-образная | Позволяет рано проверить сквозной путь через систему | Остальные возможности на первом этапе могут оставаться непроверенными | Когда нужно быстро проверить работу системы от входа до результата |

## Выбор для проекта

Для варианта 5 указана риск-ориентированная интеграция. В проекте
важным риском является передача матрицы между клиентом и сервером:
ошибка формата запроса или ответа влияет на результат работы.

При разработке сначала были соединены основной и вычислительный
модули, затем добавлены сервер и обмен по HTTP. После подключения
проверялись корректный запрос, недоступность сервера, неверные
данные, таймаут и неподдерживаемая версия запроса.
