# План тестирования MatrixDiagonalsComparator

## Цель и состояние тестирования

Цель — проверить соответствие будущей программы техническому заданию: правильность вычисления диагоналей, сравнения сумм и обработки некорректного ввода.

Код программы и автоматические тесты пока не реализованы. Приведённые ниже результаты являются ожидаемыми; выполнение этих тестов запланировано после реализации программы. В текущем репозитории CI проверяет оформление документации.

## Окружение

- Python 3.8 или новее для программы, согласно техническому заданию.
- Windows 10/11, Linux или macOS.
- Стандартный модуль `unittest` для будущих автоматических тестов.
- Python 3.12 в существующей конфигурации GitHub Actions.
- Для проверки времени обработки необходимо записать характеристики компьютера и используемую версию Python.

## Подход к проверкам

- Модульные проверки: вычисление двух сумм и сравнение с погрешностью `EPS = 1e-7`.
- Проверки ввода: размер матрицы, количество элементов в строке и преобразование чисел.
- Проверка полного сценария: ввод данных, расчёт, вывод матрицы, сумм и результата.
- Проверка производительности: обработка матрицы `500 × 500` согласно техническому заданию.

## Проверка вычислений

В записи матрицы ниже точка с запятой разделяет строки. Например, `[1, 2; 3, 4]` означает две строки: `1 2` и `3 4`.

| № | Входная матрица | Ожидаемые суммы и результат |
| --- | --- | --- |
| T01 | `[5.5]` | Главная: `5.5`, побочная: `5.5`. Суммы равны. |
| T02 | `[5, 1; 2, 4]` | Главная: `9`, побочная: `3`. Главная больше. |
| T03 | `[1, 5; 4, 2]` | Главная: `3`, побочная: `9`. Побочная больше. |
| T04 | `[1, 2; 3, 4]` | Главная: `5`, побочная: `5`. Суммы равны. |
| T05 | `[1, 2, 3; 4, 5, 6; 7, 8, 9]` | Обе суммы: `15`. Центральный элемент `5` входит в каждую сумму. |
| T06 | `[-5, -1; -2, -4]` | Главная: `-9`, побочная: `-3`. Побочная больше. |
| T07 | `[1.5, 0.2; 0.3, 2.5]` | Главная: `4.0`, побочная: `0.5`. Главная больше. |
| T08 | `[0, 0; 0, 0]` | Обе суммы: `0`. Суммы равны. |
| T09 | `[5e-8, 0; 0, 0]` | Разность `5e-8` меньше `EPS`. Суммы считаются равными. |
| T10 | `[1e-7, 0; 0, 0]` | Разность равна `EPS`. При условии равенства `abs(разность) < EPS` главная сумма больше. |
| T11 | `[1e-6, 0; 0, 0]` | Разность больше `EPS`. Главная сумма больше. |

## Проверка входных данных

| № | Входные данные | Ожидаемое поведение |
| --- | --- | --- |
| T12 | Размер `0` или `-3` | Сообщение об ошибке и повторный запрос размера. |
| T13 | Размер `2.5` или `abc` | Сообщение об ошибке: требуется положительное целое число. Повторный ввод. |
| T14 | При `n = 2` введена строка `1 a` | Сообщение об ошибке преобразования числа и повторный ввод строки. |
| T15 | При `n = 3` в строке два или четыре числа | Сообщение о неверном количестве элементов и повторный ввод строки. |

При исправлении неверной строки ранее введённые корректные строки должны сохраняться. Ошибки ввода не должны приводить к аварийному завершению программы.

## Проверка полного сценария и производительности

| № | Проверка | Ожидаемый результат |
| --- | --- | --- |
| T16 | Полный расчёт для матрицы из T02 | Выведены исходная матрица, суммы `9` и `3`, сообщение о большей сумме главной диагонали. |
| T17 | Предварительно подготовленная нулевая матрица `500 × 500` | Обе суммы равны нулю. Время расчёта сумм и сравнения не превышает одной секунды. |

Для T17 измеряется работа вычислительной части без времени ручного ввода и вывода на экран. Время вывода большой матрицы фиксируется отдельно. В протоколе испытания необходимо указать способ измерения, характеристики компьютера и фактическое время.

## Будущие автоматические тесты

Тесты вычислений и сравнения планируется разместить в `tests` в файлах `test_*.py`, используя `unittest`. После их реализации запуск из корня проекта будет выполняться командой:

```bash
python -m unittest discover -s tests -p "test_*.py" -v
```

Эта команда уже предусмотрена в CI и будет выполняться при появлении соответствующих файлов тестов.

## Критерии завершения тестирования

- Ожидаемые результаты сравниваются с фактическими, а итог каждого теста фиксируется.
- Все запланированные функциональные проверки проходят успешно.
- Некорректный ввод обрабатывается без аварийного завершения.
- Требование ко времени обработки проверено в описанном окружении.
- Автоматические тесты после их реализации проходят в GitHub Actions.

До реализации программы и выполнения проверок нельзя считать эти критерии подтверждёнными.
